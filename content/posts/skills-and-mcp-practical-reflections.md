研究 Agent 时，很容易关注模型有多强、能接多少工具。真正把任务交给它以后，评价标准会变得朴素：事情有没有做完，结果能不能用，人还需要补多少工作？

围绕工具接入，我更关心两种实际可用的方案：一是用 Skill 指导 Agent 调用 CLI，二是通过 MCP 向 Agent 提供工具能力。

在第一种方案里，Skill 说明什么时候用、怎样做、如何验收，CLI 执行查询、计算和写入；在第二种方案里，MCP 约定能力的发现与交互，由 Server 实现具体操作。**本文比较的是“Skill + CLI”与“MCP 接入”两套实际执行方案。**

两套方案可以组合使用：MCP 方案也可以通过 Skill 描述流程，Server 内部也可以调用 CLI。本文关注的是任务知识、模型决策和程序执行怎样分工，以及这种分工带来的收益与成本。

从业务提效看，我会先问四个问题：多久能把第一个任务用起来，一次任务能减少多少人工操作，结果需要多少检查与返工，以及推广到更多人后要付出多少维护成本。接口调用快几秒，只是其中一项。

工具能调用、流程能描述、任务能交付，是三个不同的验收层次。只有把这些能力放进真实业务过程，才知道节省的工作是否超过了新增的配置、核对和维护工作。

下面先用项目周报说明两种方案怎样完成同一项业务，再讨论实现、选型与评估。文中示例用于解释设计，效果算例为假设数据；协议事实附官方来源，工程取舍则是我的判断。

## 一、先分清：Skill + CLI 与 MCP 分别怎样执行任务

本文说的 Skill，指以 `SKILL.md` 为入口的 Agent Skills，而不是泛指某个产品里所有被叫作“技能”的功能。

一个 Skill 可以把任务说明、操作步骤、参考材料、脚本和模板组织在一起。它更接近一份供 Agent 使用的工作手册，必要时还带着完成工作的辅助工具。[Agent Skills 概览](https://agentskills.io/home)

CLI 是命令行接口。在本文的组合里，Agent 读取 Skill 后，通过宿主提供的命令执行能力调用 CLI，传入参数，再根据输出决定下一步。CLI 可以处理本地文件，也可以访问远端业务 API；使用命令行并不意味着数据和计算都在本机。

MCP 的全称是 Model Context Protocol。它约定 AI 应用与外部服务之间如何交换上下文和能力。承载 Agent 的应用称为宿主，它通过 MCP Client 对接 Server；Server 可以运行在本机，也可以运行在远端。模型通常不直接管理连接，而是由宿主向它提供相关能力。[MCP 架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

两种方案可以访问同一个业务后端，只是交互入口不同：

```text
Skill + CLI：用户目标 → Agent 读取 Skill → 命令执行工具 → CLI → 本地资源或业务 API
MCP：        用户目标 → Agent 选择工具 → 宿主的 MCP Client → MCP Server → 本地资源或业务 API
```

对应到一个完整任务，分工是这样的：

| 问题 | 主要由谁处理 | 以整理项目周报为例 |
|---|---|---|
| 去哪里取数据、怎么调用服务 | MCP Server、CLI 或其他工具接口 | 搜索文档、读取任务、获取代码变更 |
| 哪些数据有用、按什么步骤处理 | 任务规则、Agent 判断与程序化流程 | 确定时间范围，区分已完成、进行中和阻塞项 |
| 在哪运行、允许做什么、状态如何保留 | 宿主与执行系统 | 管理凭据、权限、超时和执行记录 |
| 怎样才算完成 | 用户要求与验收规则 | 结论有来源、时间范围正确、输出可阅读 |

比较时需要对齐业务能力与验收要求。如果一侧只有原子查询命令，另一侧已经封装好整份报告的生成流程，那么观察到的差异同时包含了流程封装程度，不能全部归因于 CLI 或 MCP。

## 二、用同一个任务，对照两种方案的执行闭环

假设有一个任务：

> 整理本周某个项目的进展，生成一份带来源的周报草稿。

两种方案都应交付同样的结果。下面的流程展示不同的接入入口，以及共同的验收要求。

```text
                    用户目标、范围与验收条件
                              │
               ┌──────────────┴──────────────┐
               ▼                             ▼
          Skill + CLI                      MCP
       读取 Skill 与命令约定          获取相关工具描述与参数约定
       调用 CLI 查询各来源            经 MCP Client 调用工具
       解析命令结果与分页信息          读取工具结果与分页信息
               │                             │
               └──────────────┬──────────────┘
                              ▼
                  去重、处理冲突、生成草稿
                              ▼
                  检查来源、日期、状态与完整性
                              ▼
                  按授权交付；有写入则回读核对
```

Skill + CLI 可以把下面这些判断写进 Skill；MCP 方案也要通过任务指令、可选的 Skill 或后端工作流落实它们。不能假设换了接口，这些判断就会自动发生：

第一，来源缺了一部分时怎么办？如果任务系统不可访问，就不能把“没有查到”直接解释成“本周没有工作”。

第二，多个来源冲突时怎么办？代码合并不一定代表功能已经上线，会议里说“准备发布”也不等于发布完成。

第三，输出怎么验收？摘要写得流畅，不代表每一句都有依据；写入接口返回成功，也不代表所有内容都被完整保存。

第四，交付边界是什么？生成草稿、写入共享文档、发送给项目群，是不同的动作，应当分别受用户授权与系统策略约束。

**CLI 与 MCP 工具都提供执行入口，任务规则指导处理方法，验收把执行动作连接到用户真正需要的结果。**

### 从周报这个业务任务看，究竟省了什么

人工整理周报，往往要切换多个系统，逐个查询、复制记录、核对状态，再按统一口径写出结论。Skill + CLI 可以把查询顺序、口径与异常处理沉淀下来，让 Agent 调用命令完成这些操作；MCP 方案则可以提供对应的查询能力，或者由服务端返回已经整理好的证据集合。

业务人员感受到的改善，应当是少查几次系统、少搬运几轮数据、少解释几遍规则，以及更早拿到可用草稿。两种方案都可以让用户从自然语言入口发起任务，不应把 Skill + CLI 理解成要求业务人员亲自敲命令。

如果 Agent 生成草稿只用一分钟，负责人却要花半小时逐条纠正，其收益可能还不如一份生成稍慢、来源清楚且只需少量复核的草稿。对于这个任务，我会优先看每份合格周报需要的人工分钟数，再看系统运行耗时。

但这个排序与业务目标有关：交互式查询更在意响应时间，定时批处理更在意吞吐量与准时交付，审批类任务则可能主要受人工等待影响。需要先找到实际瓶颈，才能判断优化命令调用或工具通信是否有意义。

## 三、Skill + CLI 的价值，是把操作经验接到可执行命令上

这套方案把熟练员工的操作经验转化为 Agent 可以复用的执行方法。如果团队已有可靠 CLI、执行环境和授权，就能从具体任务入手，把已有工具接到一套清晰的工作流程上。

Skill 通过指令影响模型行为，它的工程价值在于让这些指令有了明确的维护与复用方式。

在日常工作里，我们经常反复补充类似要求：

- 改代码前先读项目约定，完成后运行相关检查。
- 整理会议记录时，把事实、推断和待确认事项分开。
- 生成文档后检查版式，不能只检查文本有没有写进去。
- 写入外部系统后回读，确认最终保存的内容。

单次告诉模型这些要求并不困难。困难在于下一次还能不能保持一致，换一个项目或同事后还能不能复用，以及流程改变时有没有一个明确的位置可以修改。

我认为 Skill 的价值，在于把这些散落在对话里的经验变成可以审查、维护和复用的材料。

与 CLI 配合后，这些经验有了明确的执行入口。例如，Skill 规定先确认项目与时间范围，再调用查询命令，遇到分页继续读取，写入后通过对象 ID 回查；CLI 则负责实际请求、参数校验和结果输出。这种组合既可以复用已有命令，也便于人在终端复现 Agent 执行过的步骤。

经验一旦被写成具体规则，就能讨论它是否合理；一直藏在个人习惯里的经验，很难被团队共同改进。

不过，写成文件并不意味着模型已经学会。Skill 是运行时可读取的上下文，不是模型权重更新，也不会天然记住上一次执行的教训。要积累经验，仍然需要显式修改、评审和维护它。

### Skill 指导命令编排，流程会受到已有上下文影响

Skill 被加载到模型上下文后，会与用户要求、保留的历史对话、项目约定和工具结果共同影响模型判断。[Agent Skills 加载机制](https://agentskills.io/home#how-do-agent-skills-work) 据此，我认为用 Skill 指导流程时需要关注一个特点：同一份说明在不同会话里，可能让 Agent 选择不同的分支和下一步动作。

这种影响有好的一面：用户已经明确过时区、输出格式或项目范围，Agent 就可以据此选择合适的分支，不必重新询问。也有需要防范的一面：上一项任务的假设、过时的工具结果或含糊的历史要求，可能干扰当前判断。

所以，我会在 Skill 里明确输入、分支条件和完成标准，并要求任务开始时核实关键状态。对于复杂任务，还可以由宿主提供独立执行上下文，只传入必要的目标、约束和证据。**读取一份 Skill 本身不会自动创建隔离上下文，也不会清空先前对话。**

在 Skill + CLI 方案中，要进一步区分模型对命令的编排与 CLI 内部的执行。前者会受已有上下文影响；后者如果采用确定性代码，就按参数与程序逻辑运行，不会自动读取 Agent 的整段对话。只有显式传入的信息，或 CLI 自己能够访问的数据与状态，才会参与内部处理。

MCP 也有同样的边界：模型选择工具、生成参数和解释结果时，仍然受上下文影响；确定性 Server 内部的控制流则由程序约束。如果 CLI 或 MCP Server 内部又调用了模型，就还需要管理那个模型的输入。**决定流程稳定性的关键，是哪些判断留给模型、哪些步骤固化为代码，而不只是入口叫 CLI 还是 MCP。**

## 四、MCP 的价值，是让接入方式更容易复用

把业务 API 接入 Agent，除了发出请求，还要描述能力、组织参数，并约定结果与错误的表达方式。多个应用分别实现这些适配，容易形成重复工作。

MCP 为这些交互提供共同约定。它能够减少重复适配，但不会消除业务系统本身的复杂度。登录、权限、分页、限流、数据口径和写入一致性，仍然需要具体实现负责。

对应到业务提效，我更看重它在共享能力上的作用：当多个团队或多个 Agent 应用都需要查询订单、读取项目资料、创建业务草稿时，一个维护良好的共享服务有机会减少各自重复对接的成本。统一权限与业务校验也可以放在服务后端落实。前提是团队确实建设并维护了这些机制，协议本身不会自动带来统一治理。

还有一点需要说清：MCP 不只有工具调用。Server 的核心能力还包括 Resources 和 Prompts：前者提供上下文数据，后者提供可复用的交互模板。Tools 则用于执行操作。[MCP 核心能力说明](https://modelcontextprotocol.io/docs/learn/architecture#primitives)

Skill + CLI 依靠任务说明、命令帮助和输出约定协作；MCP 通过协议描述和交换能力、输入与结果。前者需要维护命令环境与说明的一致性，后者需要维护 Server、客户端兼容性与协议适配。两侧最终都要应对业务 API 的变化。

评价时应使用同一套标准：Agent 能否找到正确能力、构造有效参数、理解返回结果，并按业务要求完成任务。接入测试通过，只说明其中一部分成立。

## 五、Skill + CLI 要同时设计好知识入口与命令契约

一个 Skill 再详细，如果没有在合适的任务里被使用，效果也接近于零。

Agent Skills 的格式要求入口文件包含 `name` 和 `description`，并以渐进加载的方式组织信息：先看到简要描述，需要时再读取正文及相关材料。具体发现和加载行为仍取决于宿主实现。[Agent Skills 格式规范](https://agentskills.io/specification)

因此，**描述应当交代任务、适用条件和预期产物，帮助 Agent 判断何时使用。**

“处理文档”就很难选择。它究竟负责提取内容、修改结构、检查排版，还是发布到知识库？如果多个 Skill 都用这个描述，Agent 还要先猜一次分工。

我更倾向于写成：“在需要汇总指定项目、指定时间范围内的工作进展时使用，生成带来源的周报草稿。”一句话就交代了任务、输入范围和输出。

对于一个包含多种材料的 Skill，可以采用这样的组织方式：

```text
project-weekly-report/
├── SKILL.md                   # 适用范围、流程、验收条件
├── references/
│   ├── status-definitions.md  # 团队对任务状态的定义
│   └── cli-contract.md        # CLI 版本、参数、输出与错误约定
├── scripts/
│   └── check_report.py        # 检查必需字段和来源链接
└── assets/
    └── report-template.md     # 周报模板
```

这是目录设计示意，不是一套已经实现的工具包，CLI 程序也可以独立安装和分发。主文件可以参考下面的写法：

```markdown
---
name: project-weekly-report
description: 汇总指定项目与时间范围内的工作进展，生成带来源的周报草稿。
---

# 项目周报

## 输入

- 项目范围与时间范围。
- 可读取的任务、文档或代码仓库来源。

## 执行环境

- 按 references/cli-contract.md 检查 CLI 版本和登录状态。
- 使用结构化输出；按接口约定处理退出码、分页与部分失败。
- 只加载当前子命令需要的参数说明。

## 流程

1. 明确时区与起止时间；有歧义时先消除歧义。
2. 通过 CLI 查询来源，保留链接、状态与更新时间，处理全部所需分页。
3. 合并同一事项的重复记录，保留冲突信息。
4. 区分已完成、进行中、阻塞和待确认事项。
5. 按模板生成草稿，检查关键结论是否有证据。

## 验收

- 不把计划描述成已完成事实。
- 不自行补造负责人、日期或进度。
- 明确列出缺失来源和相互矛盾的信息。
- 发布行为遵循用户授权和宿主权限策略。
```

这份说明的重点是把输入、执行约定和验收条件说清楚。

CLI 一侧则需要稳定的命令契约：参数含义明确，输出可解析，退出状态可判断，非交互执行不会突然等待输入。可供机器读取的结果与诊断日志也应能区分。哪些字段稳定、哪些错误可以重试、版本不兼容时如何停止，都值得写进参考文件。

Skill 负责说明如何使用这些约定，CLI 负责真正实现它们。如果命令只能输出不断变化的人类阅读表格，Agent 就要额外猜测和解析；把这种不稳定性写进更长的 Skill，通常解决不了根本问题。

## 六、一个工具好不好用，不能只看接口能不能返回成功

面向程序员的 API 和面向 Agent 的工具，使用方式有明显差异。程序员通常提前知道自己要调用什么；Agent 经常要在运行时从若干候选能力中做选择。

因此，我会特别关注工具是否把意图表达清楚。

例如，`operate(data)` 虽然灵活，却把大量解释工作推给了模型。相比之下，`search_documents(query, cursor)`、`read_document(document_id)`、`create_document_draft(title, content)` 更容易理解，也更容易划分权限。

CLI 也应采用同样清晰的动作边界。例如，示意命令 `workctl documents search` 与 `workctl documents create-draft`，比把所有行为藏在一个复杂参数里更容易使用。这些名称只是设计示例，不对应已安装的工具。MCP 的参数 schema 可以描述结构约束，CLI 的参数解析器也可以校验类型与必填项；两者都仍需校验业务语义。

接口粒度也要适中。过细会增加往返次数，把简单任务拆成十几次调用；过粗又可能隐藏副作用，让授权和恢复变得困难。我倾向于围绕意图清晰、输入可校验、结果可验证的业务动作设计接口。

结果设计也一样。返回“创建成功”，对接下来的工作帮助有限；返回对象 ID、链接、最终状态和需要注意的部分失败，Agent 才有条件继续判断。

我还希望错误信息能区分几种情况：输入不合法、没有权限、触发限流、暂时不可用，以及执行结果未知。它们需要完全不同的后续动作。

尤其是“执行结果未知”：请求超时不等于服务端没有完成写入。此时直接重试，可能创建两份文档、两条任务，甚至产生重复通知。接口能提供幂等键或状态查询入口，往往比 Skill 里多写一句“谨慎重试”更有效。

## 七、上下文是预算，不能把“装得多”当成“懂得多”

我不太认同用安装了多少 Skill、CLI 或 MCP Server 来衡量 Agent 的能力。两种方案都需要管理任务说明、能力描述和执行结果占用的上下文。

工具与说明材料增加后，模型需要处理的候选项也会增加，其中可能包含重复、冲突或无关信息。具体影响需要评估，但设计目标很明确：让 Agent 在做决定时拿到足够的信息，同时减少不必要的阅读与选择。

### 权限可以收窄可见范围，按需加载还需要任务选择

在 MCP 接入中，服务端可以根据身份限制可访问的数据，并在实现支持时按授权过滤工具列表；宿主也可以按项目或任务启用不同的工具集合。MCP 工具规范允许工具列表随请求授权范围变化。[MCP 工具列表规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#listing-tools)

这种设计能够间接减少进入模型上下文的无关信息，但还需要区分三件事：

| 环节 | 回答的问题 | 常见实现 |
|---|---|---|
| 权限过滤 | 当前身份允许访问什么 | 服务端授权、租户与项目隔离 |
| 任务选择 | 允许访问的内容里，这次需要什么 | 工具筛选、搜索、资源定位 |
| 按需读取与注入 | 什么时候读取多少，又把哪些内容交给模型 | 延迟加载、分页、摘要、宿主上下文组装 |

用户有权访问一万个文档，并不意味着应该把这些文档都加载进来。反过来，客户端把一个工具隐藏起来，也不能代替服务端鉴权；只在调用时拒绝未授权请求，也未必能减少已经注入的工具描述。

**权限划定可访问范围，任务相关性用于选择本次所需内容，宿主负责组装模型输入。** 按需加载需要这几层配合，单独配置权限还不够。

Skill + CLI 同样可以配合权限与按需读取：业务后端根据 CLI 使用的身份限制数据范围，Skill 指导 Agent 只读取当前子命令的帮助，查询命令支持时再通过项目、时间和字段参数收窄结果。安装一个 CLI 不等于需要把全部帮助文本放进上下文，命令列表可见也不等于身份有权执行所有操作。

### 客户端与服务端各有职责，两种方案都能分担上下文处理

当 Agent 按 Skill 编排一系列 CLI 命令，而 MCP 工具把整段业务处理封装在 Server 内部时，前者的中间过程更多留在宿主侧，后者更多留在服务端。但这描述的是两种具体实现，不能直接归纳成“Skill + CLI 管客户端上下文，MCP 管服务端上下文”。CLI 也可以调用远端聚合接口，MCP Server 也可以只提供本地的细粒度操作。

这里应当区分模型输入、业务数据和执行状态。后两者可以为模型提供上下文，但只有实际送入模型的部分，才占用本次调用的上下文窗口。

| 所在位置 | 可以负责的工作 | 需要明确的边界 |
|---|---|---|
| Agent 宿主侧 | 加载 Skill、组装模型输入、选择工具描述、裁剪历史消息、保留任务摘要 | 宿主可以在本地，也可以部署在云端；不等同于狭义的 MCP Client 通信组件 |
| CLI 进程及其调用的后端 | 参数解析、数据过滤、批处理、文件落盘、分页与缓存 | 取决于 CLI 实现；磁盘文件与命令输出不会天然成为模型记忆 |
| MCP Server 及业务后端 | 访问控制、检索过滤、聚合、分页、缓存；按实现需要保存中间状态或提供结果句柄 | 这些是具体服务的实现选择，MCP 不自动提供完整业务状态管理 |
| 模型调用边界 | 接收宿主实际提交的上下文，据此推理和生成结果 | 服务端保存的数据不会因为“已经接入”就自动进入模型上下文 |

比如，服务端可以从一万条记录中筛出本周相关的二十条，返回摘要与原始记录入口；宿主再决定把哪些摘要交给模型，必要时继续读取详情。这样两侧都在控制信息量，只是控制的阶段不同。

MCP 官方也明确说明，协议关注上下文交换，不规定 AI 应用如何管理这些上下文。若 Server 内部还运行另一个 Agent，那么它还需要管理内部模型的上下文，不能假设它会自动继承外层完整会话。[MCP 的职责范围](https://modelcontextprotocol.io/docs/learn/architecture#scope)

### 按需加载之后，仍要保留证据入口

对于 Skill，我会把稳定的主流程放在入口，把罕见分支和详细材料拆出去。对于工具，我会优先按当前任务提供相关能力，支持时再使用动态发现。对于工具返回值，我会保留关键字段、分页信息和来源，避免把整份原始数据无差别塞进上下文。

在 Skill + CLI 里，还可以让命令把大结果写入文件，先返回摘要与路径，再按需读取相关片段；MCP 工具也可以通过资源入口或业务结果句柄提供类似能力。无论哪一侧，把数据留在上下文之外后，都要保证 Agent 能定位、读取并判断它是否仍然有效。

也不能为了省 token 只保留摘要。模型可能恰好需要原文里的一个限制条件或一个日期。更合理的做法是先提供可判断相关性的摘要，再保留读取原始证据的入口。

这些安排的业务价值，是减少无关信息造成的耗时与误判，同时保留复核结论所需的证据。

## 八、哪些判断留给 Agent，哪些交给 CLI 或 Server

上下文准备好之后，还要决定由谁作判断。模型适合处理语义和不完全明确的问题，例如组织说明、解释信息缺失、选择业务分支；明确的计算、校验和状态约束，则更适合交给代码。

| 需求 | 我倾向放在哪里 | 原因 |
|---|---|---|
| 判断报告是否回应用户关心的问题 | 任务规则与模型 | 需要理解语义和任务背景 |
| 校验日期格式、必填字段、数字合计 | CLI、辅助脚本或 MCP Server 的代码 | 规则明确，适合机械验证 |
| 控制用户可访问的项目 | 服务端权限系统 | 不能依赖模型自觉遵守 |
| 防止重复创建外部对象 | 工具后端与状态存储 | 需要幂等机制和持久记录 |
| 解释部分失败并决定如何交付 | 模型与执行系统共同处理 | 既有任务判断，也有状态约束 |

比如，“金额必须精确”应该促使系统使用可靠的计算与校验，而不是只让模型多检查一遍。“不能重复发送”应该落实到发送记录和去重逻辑，而不是仅写成提醒。

我的判断标准是：**如果一条要求必须每一次都成立，就不要只把它放在提示词里。**

这也解释了为什么 Skill 不能替代工作流引擎。涉及跨天等待、审批、并发竞争、断点恢复或事务补偿时，需要可持久化的执行状态。Skill 可以指导其中的任务处理，但不能仅凭 Markdown 保证流程恢复。

CLI 可以作为持久化工作流的启动与查询入口，MCP 工具也可以如此。两种入口都不自动提供恢复能力；需要看它们背后的程序是否真正保存了状态、处理了幂等与补偿。

## 九、权限边界要落在系统里

接入外部能力后，Agent 能做的事情会增加，相应地，错误动作的影响也会变大。

我会区分三个问题：用户希望做什么，Agent 建议做什么，以及系统实际允许做什么。这三者有关联，但不能互相替代。

用户要求“整理资料”，并不自动授权删除原始资料；工具描述声称“安全”，也不能替代服务端校验。认证证明身份，授权决定这个身份能访问哪些资源、执行哪些动作。

Skill + CLI 还要管理命令执行边界。允许 Agent 使用某个业务 CLI，不应被理解为授予任意 shell 操作的权限。路径、引号、重定向和命令拼接都可能改变实际执行含义；如果宿主支持结构化参数传递或受限执行入口，应尽量使用。CLI 使用的业务凭据与本地进程权限也要分别管理，不能指望 Skill 中一句“只做安全操作”代替限制。

MCP 的官方安全文档讨论了令牌透传、代理授权等风险。接入标准协议，并不会自动补齐应用层的权限设计。[MCP 安全实践](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)

还有一个与日常使用更接近的问题：文档、网页、仓库文件和工具返回内容里，都可能出现看起来像指令的文字。例如，一篇被读取的文档要求 Agent 把本地凭据发送到某个地址。

这些内容应当作为待处理的数据，不能因为被读到就获得指挥 Agent 的权限。Skill 本身也要审查来源，尤其是包含脚本、安装命令和网络请求的第三方 Skill。

我的做法建议是把几件事分别落实：凭据通过受控机制提供，工具权限按任务收窄，敏感写操作在执行前校验目标与授权，日志保留必要证据并避免泄露秘密。

权限设计也影响业务效率。明确授权范围内的工作应当顺畅推进，确认应集中在目标含糊、超出既有授权或后果重大的决定上，避免每个机械步骤都让用户重复批准。

## 十、Skill + CLI 与 MCP，应该怎样选

### 先判断业务瓶颈，再判断接入方式

前面的差异可以归结到一个选型顺序：先找到业务瓶颈，再判断哪种接入方式能以较低成本解决它。

| 业务现状 | 可以优先验证的方案 | 希望获得的改善 |
|---|---|---|
| 操作经验分散，但已有可用 CLI，流程还在频繁调整 | Skill + CLI | 减少反复讲解和手工操作，更快验证新流程 |
| 多个团队和宿主反复接同一组业务能力 | 共享 MCP 服务，或已有的统一服务入口 | 降低重复接入、升级与权限管理成本 |
| 某个流程高频、稳定，却反复让模型判断下一步 | 把稳定步骤封装成 CLI 子命令或 MCP 工具 | 减少模型往返、遗漏与执行波动 |
| 用户主要耗时在核对结果和修正错误 | 先完善数据口径、证据与校验 | 降低返工率，减少每次任务的人工介入 |
| 大量时间花在等审批、等数据或跨部门确认 | 优化状态通知、职责和业务流转 | 缩短完整交付周期，避免只优化工具调用速度 |

Skill + CLI 也能通过统一分发、共享后端和受控执行平台服务团队；MCP 也可以作为个人本地工具使用。规模化能力来自部署与维护方式，不能只看入口名称。

对流程还不稳定的业务，保留一部分模型判断，有利于处理输入差异和例外；当规则已经稳定、执行频率提高，就可以把适合固化的步骤下沉到代码。这个变化可以发生在任何一套方案里，不需要把“从 CLI 换成 MCP”当作成熟度的必经路径。

### 再核对宿主与现有工具链

业务方向确定后，还要检查落地条件。团队主要处理本地文件、已有稳定命令，并重视终端复现时，Skill + CLI 值得优先验证；宿主限制通用命令执行，却支持经过授权的 MCP 接入时，MCP 可能更容易落地。两种条件都具备，就比较安装分发、认证、升级和故障排查的总成本。

有些缺口需要额外能力：从大量资料中找到相关事实，需要检索；跨会话等待和恢复，需要持久化工作流。这些能力都可以通过 CLI 或 MCP 暴露，单换入口不会补齐它们。

### MCP 会比 Skill + CLI 更快吗

在某些实现里会，但我不会把它写成两者的固有性能差异。Skill + CLI 本身已经包含可执行程序，并不是每一步都只能由模型处理。真正应当比较的是：**完成同一项任务时，模型参与了多少轮决策，CLI 或 Server 内部完成了多少工作，传输了多少数据。**

例如，同样是“读取五个来源并合并统计”，一种实现让 Agent 按 Skill 逐个调用 CLI 子命令、查看结果、再决定下一步；另一种把稳定的数据处理流程封装在一个 MCP 工具里，由后端批量读取、合并并返回结果。后一种可能减少模型往返与中间数据传输，从而更快。这里的优势来自批处理和程序化执行，而比较双方的封装粒度并不相同。

如果 Agent 按 Skill 的指引调用一个完成相同批处理的 CLI 子命令，也能减少这些往返。反过来，若 MCP 只提供细粒度工具，Agent 仍需逐步推理调用，就不会自动省下模型耗时。

在封装粒度接近时，还要比较执行开销：CLI 可能反复启动进程，MCP 的常驻 Server 可能复用连接与缓存；但 CLI 也可以连接常驻后端，而 MCP Server 也可能冷启动或再次创建子进程。网络、鉴权、序列化、排队和额外模型调用都取决于部署方式。不能把“CLI 一定本地、MCP 一定远程”作为测速前提。

可以用一个简化的耗时拆分来理解，实际存在并行时，应看关键路径而非直接相加：

```text
端到端耗时 ≈ 模型决策与生成耗时
           + 工具执行耗时
           + 通信、排队与启动开销
           + 必要的校验与重试耗时
```

**速度优化应当围绕实际耗时最多的步骤展开。** 两种方案都能通过批处理减少模型往返；是否值得做，还要看节省的运行时间能否改善业务交付周期。

## 十一、一些容易让效果变差的做法

**把所有规则写进一个巨大的 Skill。** 结果是任务无论大小，都要理解一大堆条件分支。我更倾向于围绕完整任务组织 Skill，把共同配置单独维护，而不是围绕每个 API 写一份重复说明。

**把失败统一处理成重试。** 限流可以等待，输入错误需要修正，权限不足需要处理授权，写入超时需要核实状态。没有分类的重试，很容易放大问题。

**在 Skill 里硬编码易变环境。** 个人绝对路径、特定工具名称、某台机器上的软件位置，都可能破坏可移植性。格式能被识别，只是复用的第一步；工具契约、依赖和权限也需要匹配。

**把终端里的成功当成 Agent 环境里的成功。** 人工终端可能已有登录状态、别名和交互输入，Agent 的执行环境却没有。Skill + CLI 要明确安装版本、工作目录、配置与非交互运行要求；MCP 则要核对 Server 启动环境、连接与认证配置。两侧都要测试真实运行环境。

**遇到一次问题就追加一条规则。** 单条规则看起来都有道理，叠加后却可能互相冲突。修改 Skill 时，应当像修改代码一样整理整体逻辑，而不是无限追加补丁。

**只保留成功案例。** 真正能暴露边界的，往往是空结果、来源冲突、超长文档、权限缺失和中途失败。如果只拿最顺利的任务演示，很难知道方案是否可靠。

## 十二、怎样判断它们是否真的带来了改善

### 业务指标应当先于工具指标

我会先建立原有工作方式的基线，再观察引入 Agent 后的变化。需要同时记录成功与失败任务，不能只挑生成顺利的样本。

| 业务指标 | 建议统计口径 | 能回答的问题 |
|---|---|---|
| 人工投入 | 每项任务的准备、澄清、复核、修正与故障处理时间 | 员工究竟少做了多少工作 |
| 交付周期 | 从提出需求到结果被业务接受的时间，包含等待与返工 | 业务是否更早拿到可用结果 |
| 按期一次验收通过率 | 无需修正且按期通过的任务数 / 同批应交付任务数 | 自动产出是否稳定、及时可用 |
| 单位合格交付成本 | 同批任务的总成本 / 合格交付数，含失败消耗与分摊成本 | 自动化有没有降低实际成本 |
| 推广成本 | 新用户或团队的配置、培训、授权与支持投入 | 能否以可承受的成本扩大使用 |
| 流程变更成本 | 规则变化后的修改、验证和重新分发投入 | 方案能否跟上业务变化 |

节省的人工时间代表可以重新分配的产能，不一定直接等于现金支出下降。人工小时与货币费用应分别记录；需要计算总成本时，再用一致的口径折算，并说明初期建设费用怎样分摊。比较双方应使用相同任务范围、统计周期和质量标准。

举一个假设算例：同样合格的一项任务，原来需要 30 分钟人工操作，采用任一种方案后，准备、复核、修正及失败处理的平均人工投入为 10 分钟。每月完成 100 次，就释放约 33.3 小时；再扣除额外的 8 小时维护投入，净释放约 25.3 小时。这还没有扣除初期建设的人力投入，模型与服务费用也需另计。

系统运行时间要单独看。Agent 自动处理了 5 分钟，期间人可以做其他工作，这 5 分钟就不应直接算作人工投入；它仍然属于交付周期的一部分。同步等待的交互任务，还需要考虑这段等待对使用体验的影响。

### 工程指标用于解释收益与定位问题

业务指标说明是否值得投入，工程指标则帮助解释收益来自哪里、问题出在哪里。

可以先比较同一 CLI 在没有专项 Skill 与加入 Skill 后的表现，观察任务知识的贡献；再比较同一后端能力通过 Skill + CLI 与 MCP 暴露时的表现，观察接入方式的差异。后一组应提供相当的业务规则与参考材料，尽量对齐工具粒度、模型、任务输入和权限，多运行几次，避免把说明是否齐全或一次偶然成功误当成接口优势。

我会记录这些指标：

| 维度 | 观察内容 |
|---|---|
| 能力选择 | Skill 触发、命令或工具选择、参数构造在哪一步出错 |
| 上下文使用 | 加载了哪些说明和数据，是否遗漏证据或引入无关内容 |
| 执行开销 | 模型轮次、token、工具调用次数及各阶段耗时 |
| 失败恢复 | 超时、权限不足、结果未知时的处理是否正确 |
| 外部副作用 | 是否出现重复写入、错误目标或未经授权的动作 |
| 变更影响 | 工具升级后哪些环节失效，需要修改哪些说明与代码 |

这些指标不能互相替代。少调用几次工具，如果换来的是遗漏证据，就不一定是优化；完成率提高，如果依赖大量人工补救，也要把补救成本算进去。

回归任务也应该进入版本管理。记录 Skill、CLI、MCP Server 与宿主的版本及相关环境，才能在结果变化时定位原因。

如果专门比较速度，还应尽量保持数据范围、模型配置与输出质量要求一致，分别记录冷启动和缓存命中的表现、模型轮次及各阶段耗时。多次运行后比较中位数和较慢请求的耗时，才能区分收益究竟来自减少推理轮次、后端批处理，还是缓存和网络条件的变化。

## 十三、如果从零开始，我会先做一个小闭环

我会选择一个高频、边界明确、结果容易检查的任务，比如生成项目周报草稿、整理一类文档，或者按固定标准审查变更。

先记录它当前的操作时间、等待时间和常见错误，明确希望改善哪一项，并约定合格产物的标准。这样后续无论选择 Skill + CLI 还是 MCP，都能检验是否解决了原来的业务问题。

如果已有可靠 CLI，我会先在真实执行环境里完成一次，把反复解释的要求整理成 Skill，把校验和稳定批处理放进 CLI 或辅助脚本。如果现有宿主已经有成熟的 MCP 接入，则先复用它，补齐任务规则与验收。等业务闭环成立，再评估是否需要另一种入口，避免为了比较技术先重复建设两套实现。

接下来补充几组正常与异常任务：来源齐全时怎么做，缺失一部分数据时怎么做，写入失败时怎么恢复，以及不该使用这个 Skill 的任务是否会被误触发。

等这一个闭环稳定以后，再扩大范围。这样，每增加一个 Skill 或工具，都有具体的问题作为依据，也有一个可以比较的结果。

我认为团队长期值得积累的，正是这一套共同维护的材料：任务定义、操作经验、工具契约、评估案例和失败记录。模型和客户端会变化，这些材料仍然可以帮助团队判断下一套方案是否更好。

## 十四、我最终关心的，是每次合格交付需要多少投入

Skill + CLI 让我重新看待了已有命令工具的价值：把工作经验写成可复用的指引，把确定性操作交给程序，就能让 Agent 在熟悉的工具链上完成更完整的任务。

MCP 则让我重新看待了工具接入：当能力通过共同协议暴露，AI 应用就有机会减少重复适配，把更多精力放在怎样使用这些能力上。

从业务提效看，两种方案都需要回答同样的问题：任务是否更早完成，员工是否少做了重复劳动，结果是否更容易验收，扩大使用后是否仍然值得维护。

我会同时看结果与证据：交付是否合格，引用了哪些来源，改动了哪些对象，人又为它投入了多少检查和修正。这样才能把一次漂亮的演示与持续可用的业务能力区分开。

**对我来说，Skill + CLI 与 MCP 最值得比较的，是以多少总投入，稳定完成多少合格业务任务。** 这个标准会把注意力带回真正需要改进的地方：重复劳动、等待、返工，以及团队长期维护这套能力的负担。
